## Архитектурный манифест: Я.Д-Пылесос (YA.D-Pylesos)

Этот документ описывает инженерный подход, примененный при разработке утилиты для скачивания данных с Яндекс.Диска на NAS-серверы Linux arm64 / x86/64. 

Разработка ведется с применением AI-Assisted Development (LLM). Автор выступает в роли Product Owner / Project Manager / System Architect / QA Engineer, формулируя архитектурные принципы и ограничения, применяя междисциплинарные методологии аудита и проводя краш-тесты. ИИ используется в роли Junior/Middle разработчика для генерации boilerplate-кода и реализации бизнес-логики.

### 1. Фундаментальные принципы (Ограничения среды)

Проект изначально проектировался как инфраструктурный компонент, работающий 24/7 на слабом железе с механическими дисками. Были заложены железобетонные принципы:

*   **Анти-бан API (Мимикрия):** Абсолютный приоритет минимизации вероятности блокировки IP-адреса Яндексом над скоростью работы. Алгоритм должен вести себя как человек.
*   **Бережливость HDD (RAID-friendly):** Абсолютный приоритет корректной физической записи на диски над скоростью. Многопоточная запись не должна фрагментировать файловую систему и убивать IOPS.
*   **Безопасность данных (ACID & Zero Trust):** Ни один битый файл не должен заменить оригинальный. Все операции с диском и базой данных должны быть атомарными. Входные данные (аргументы, кэш) строго валидируются.
*   **Самоисцеление и Graceful Degradation:** При обрыве связи, сбое питания или падении контейнера скрипт должен корректно продолжить работу с точки остановки. При критических сбоях сети — плавно деградировать или завершить работу (Fail-Fast).

### 2. Аудит надежности (FMEA и Кросс-дисциплинарные методы)

Для поиска скрытых уязвимостей применялась методология FMEA (Анализ видов и последствий отказов), а также 40 инструментов из смежных дисциплин (Проектный менеджмент, Авиация, Медицина, Юриспруденция, Биология).

**Выявленные и устраненные угрозы:**

*   **Атомарность склейки (RPN 270):** При моргании света во время склейки кусков `.part.N` в единый файл, на диске мог остаться недоклеенный файл. 
    *   *Решение:* Внедрен маркерный файл `.gluing`. При рестарте скрипт видит маркер, безжалостно удаляет все куски и качает файл заново. Финальное переименование происходит через `os.replace` (атомарная операция на уровне ОС).
*   **Хаотичные сбои (Cynefin Framework):** При критических ошибках файловой системы (Read-Only, переполнение диска, нехватка инодов) скрипт не должен пытаться "выжить", забивая логи. 
    *   *Решение:* Внедрен Апоптоз (Программируемая гибель). При ошибке ОС скрипт мгновенно завершает работу (Fail-Fast). Добавлена предстартовая проверка свободного места и инодов перед Ступенью 3.
*   **Блокировка БД (Database is locked):** При параллельном запуске двух контейнеров SQLite блокировал базу данных.
    *   *Решение:* Внедрена изоляция баз данных (BL-DB-Split). Каждая ссылка использует свой файл `db/<имя_контейнера>.db`. Глобальные `.lock` файлы полностью удалены как атавизм.
*   **Обнуление БД на лету:** При повреждении БД скрипт автоматически перемещает её в карантин, создает пустую и завершает работу, чтобы при следующем запуске перестроить кэш с нуля, исключая потерю данных.

### 3. Архитектура данных и памяти (SSOT, DAL и Mark-and-Sweep)

Изначально скрипт хранил карту локального диска и дерева Яндекса в оперативной памяти. При скачивании папок с 40 000+ файлов потребление RAM достигало 800 МБ, что грозило OOM-kill на NAS.

**Рефакторинг (Версия 13.0+):**

*   **SSOT (Single Source of Truth):** Словари в RAM полностью удалены. Единственным источником истины стала база данных SQLite (WAL-режим для конкурентного чтения).
*   **Инкрементальный скан (Mark and Sweep):** При повторных запусках скрипт не удаляет таблицу локальных файлов и не сканирует диск заново. Он проверяет `mtime` (время изменения) и размер. Если файл не изменился, просто ставится флаг `scanned=1`. Это радикально снизило износ RAID-массива при частых запусках.
*   **Потоковая обработка (Streaming Queue):** Очередь скачивания не грузится в память. Скрипт берет файлы из БД строго по одному (`LIMIT 1`).
*   **Профилирование:** Внедрен флаг `--trace-mem` (на базе `tracemalloc`) для точного выявления строк кода, потребляющих RAM. Тесты на 65 000 файлов показали потребление < 100 КБ.

### 4. Физика дисков и оптимизация IOPS

*   **Паттерн "Переборка" (Bulkhead):** Многопоточное скачивание реализовано не через `seek` в один файл, а через запись в изолированные `.part.0`, `.part.1`. Это превращает деструктивный Random Write в последовательный (Sequential Write). 
*   **Гомеостаз (Нагрузка на CPU):** Раз в 5 минут скрипт читает `/proc/loadavg`. Если NAS захлебнулся (например, идет проверка RAID), скрипт снижает количество потоков до 1, уступая ресурсы системе.

### 5. Сетевая устойчивость, Анти-бан и Умный VPN

Взаимодействие с API Яндекса спроектировано на основе Теории игр (AIMD).

*   **Адаптивные паузы:** Если Яндекс отвечает `200 OK`, пауза плавно сокращается. При ошибке `429` пауза резко умножается.
*   **Детекция "тихого бана":** Если API возвращает HTML-страницу вместо JSON, скрипт воспринимает это как блокировку и меняет User-Agent.
*   **Адаптивный CDN:** Модуль скачивания (CDN) обучаем. При обрывах связи он увеличивает паузы между чанками, логируя это, чтобы не "долбить" сервера Яндекса.
*   **Умный авто-VPN (mihomo):** При срабатывании бана (5 раз подряд) скрипт автоматически генерирует YAML-конфиг из `link*.txt` (поддержка VLESS/Reality), запускает туннель `mihomo` в режиме `fallback`, проверяет открытие порта 7890, делает тестовый запрос и маршрутизирует трафик API через прокси.
*   **API Watchdog:** Внедрен фоновый мониторинг процесса `mihomo` (через порт 9090). При зависании или падении туннеля происходит автоматический перезапуск (до 3 попыток), иначе скрипт вызывает Апоптоз (Fail-Fast).
*   **Обход SSL-ошибок:** Флаг `--ssl-off` отключает проверку сертификатов для обхода багов Яндекс.Диска (просроченные сертификаты на CDN-узлах).

### 6. Качество кода и наблюдаемость (Observability)

*   **Проектирование по контракту (Design by Contract):** Функции скачивания защищены строгими проверками (контракты DbC). Если размер файла не совпал — скрипт падает с `ValueError`, не допуская появления битых данных.
*   **Статический анализ:** Код прошел проверку линтерами Ruff и Vulture. Цикломатическая сложность (CC) **всех** функций строго снижена до `< 10` (Ранг A/B по стандарту McCabe) через хелперы и Guard Clauses.
*   **BDD-разработка:** Сложная логика (сигналы `Ctrl+C`, статусы контейнеров) пишется строго по утвержденным BDD-сценариям.
*   **Оркестрация (SSOT):** Интерактивное управление списком ссылок (`source_links.txt`) перенесено из Bash в Python CLI. Bash стал "тонким клиентом" для запуска Docker-контейнеров.
*   **Фактор автобуса (Bus Factor):** Логи спроектированы так, чтобы быть самообъясняющимися. Используются эмодзи (📄, 📁, 🗑) и цветовое кодирование по уровням логирования (`record.levelno`).

### Тестирование

Тестирование проводилось на NAS QNAP D4 arm64 с HDD WD UltraStar RAID1 и Fedora 44 WS SDD. В тестировании были использованы ссылки с объемом информации до 3.5TB и 65 000 файлов. Анонимный доступ и авторизация (OAuth 2.0, cookies). 

### Технологический стек

*   **Ядро:** Python 3.12 (Threading, SQLite3, requests, PyYAML, urllib3).
*   **Инфраструктура:** Docker (изоляция, python:3.12-slim).
*   **VPN-движок:** mihomo (Clash.Meta) — встроенный бинарник.
*   **Оркестрация:** Bash (GNU Coreutils / BusyBox).
*   **Аудит:** FMEA, TRIZ, Cynefin, Radon, Ruff, Vulture.

### Перспектива (Долгосрочное развитие)

*   **Полная автоматизация (Cron):** Внедрение флага `--batch-auto` для тихого запуска по расписанию без интерактивного меню.
*   **Интеграция с Telegram:** Модуль уведомлений для отправки статусов скачивания и критических ошибок.
