# Архитектурные решения (ADR) — сводный реестр

Полный реестр архитектурных решений проекта. Исторические записи (0001–0016) велись отдельными файлами в каталоге ADR/ и консолидированы здесь. Решения 2026 года (0017–0019) внесены по итогам спринтов.

## ADR-0001: Переход на SSOT (RAM → SQLite)

### Контекст
Изначально скрипт хранил карту локального диска и дерева Яндекса в оперативной памяти (Python dicts). При скачивании папок с 40 000+ файлов потребление RAM достигало 800 МБ, что грозило OOM-kill на NAS.

### Решение
Полностью отказаться от словарей в RAM. Перенести кэш дерева, очередь скачивания и MD5-хэши в базу данных SQLite (WAL-режим). База данных стала Единственным источником истины (SSOT).

### Последствия
*   **Плюсы:** Потребление RAM снизилось до 50-100 МБ независимо от размера папки. Исключена вероятность OOM-kill.
*   **Минусы:** Добавлена зависимость от дискового I/O. Потребовалось внедрение паттерна Unit of Work для пакетной записи в БД.

## ADR-0002: Инкрементальный скан диска (Mark and Sweep)

### Контекст
При каждом запуске скрипт удалял таблицу локальных файлов и заново сканировал диск. Это вызывало сильную фрагментацию и износ RAID-массива на NAS.

### Решение
Внедрён алгоритм Mark and Sweep. В таблицу `local_files` добавлены колонки `mtime` и `scanned`. При запуске скрипт помечает все записи как `scanned=0`. При обходе диска сравнивает `mtime` и размер: неизменённый файл — `scanned=1`. В конце удаляются только записи с `scanned=0`.

### Последствия
*   **Плюсы:** Скорость Фазы 1 возросла до миллисекунд. Износ диска минимизирован.
*   **Минусы:** Требуется аккуратное управление флагом `scanned` при падениях (восстанавливается при следующем запуске).

## ADR-0003: Изоляция БД для каждой ссылки (BL-DB-Split)

### Контекст
Единая база (`yadpylesos.db`) давала `database is locked` при параллельном скачивании двух ссылок.

### Решение
Каждая ссылка (контейнер) использует свой файл `db/<имя_контейнера>.db`.

### Последствия
*   **Плюсы:** Отсутствие блокировок при параллельной работе. Очистка данных — удалением файла.
*   **Минусы:** `--db-stats` сканирует директорию по нескольким файлам.

## ADR-0004: Удаление глобальных .lock файлов

### Контекст
Механизм глобальных `.lock` файлов с проверкой PID был сложным и хрупким.

### Решение
Логика `.lock` полностью вырезана из Bash и Python.

### Последствия
*   **Плюсы:** Упрощение кода, нет «зависших» lock-файлов после жёстких перезагрузок.
*   **Минусы:** Защита от дублей — на уровне Docker inspect и .pid.

## ADR-0005: Авто-VPN (mihomo, HTTP-прокси) — ИСТОРИЧЕСКОЕ, заменено ADR-0018

### Контекст
SOCKS5 требовал PySocks; url-test группа mihomo пинговала все сервера раз в 5 минут (нагрузка CPU); требовался обход банов.

### Решение
mihomo (Clash.Meta) с группой `fallback`, HTTP-прокси вместо SOCKS5 (mixed-port поддерживал HTTP из коробки).

### Последствия
*   **Плюсы:** Отказ от PySocks, снижение CPU.
*   **Минусы:** Ручное управление процессом через subprocess.Popen.
*   **Статус:** Решение отменено миграцией на Xray-core (см. ADR-0018). Историческая ценность — генеалогия порта 7890.

## ADR-0006: Безопасный YAML (PyYAML) — ИСТОРИЧЕСКОЕ

### Контекст
Ручная генерация YAML-конфига mihomo через f.write ломалась на спецсимволах имён серверов.

### Решение
Генерация через yaml.dump() (PyYAML в образе).

### Последствия
*   **Плюсы:** 100% защита от синтаксических ошибок YAML.
*   **Статус:** Актуально для эпохи mihomo; после миграции на Xray конфиги генерируются в JSON через json.dump (аналогичное решение, та же мотивация).

## ADR-0007: API Watchdog для mihomo — ИСТОРИЧЕСКОЕ, эволюция в ADR-0018

### Контекст
Процесс mihomo мог зависнуть или упасть без завершения Python, скачивание продолжалось вхолостую.

### Решение
Daemon-поток VpnWatchdog: раз в 60 сек проверка poll() и HTTP API (порт 9090), перезапуск до 3 попыток, иначе Апоптоз.

### Последствия
*   **Плюсы:** Отказоустойчивость длинных (cron) скачиваний.
*   **Статус:** Механизм watchdog сохранён в Xray-версии (poll + тестовый запрос туннеля; логика HTTP-API mihomo не актуальна).

## ADR-0008: Перенос source_links.txt в Python CLI

### Контекст
Парсинг списка через Bash `cut -d'|'` ломался на пробелах в путях; не хватало Tab-автодополнения.

### Решение
Интерактивное управление перенесено в Python: модуль `csv` для парсинга, `readline` для автодополнения, валидация ввода (Poka-Yoke). Внедрена rw-подача файла (монтирование поверх ro-каталога конфигурации).

### Последствия
*   **Плюсы:** Пробелы/спецсимволы в путях; UX; Bash — «тонкий клиент».
*   **Минусы:** Менеджер стартует в отдельном контейнере (~1-2 сек).

## ADR-0009: Логика Ctrl+C (отвязка от терминала)

### Контекст
`docker logs -f` блокировал терминал; Ctrl+C убивал Bash, оставляя контейнер-«зомби».

### Решение
`docker logs -f` в фоне (`&`), PID сохраняется, SIGINT перехватывается: убивается только просмотр логов, контейнер продолжает работать; печатается инструкция reconnect.

### Последствия
*   **Плюсы:** «Свернуть» скачивание, не убив контейнер.
*   **Минусы:** Остановка контейнера — вручную (docker stop).

## ADR-0010: Атомарная замена файлов (os.replace)

### Контекст
`os.remove + os.rename` оставляло окно потери файла при сбое питания между операциями.

### Решение
`os.replace(src, dst)` — атомарная замена на уровне ядра.

### Последствия
*   **Плюсы:** Гарантия сохранности при сбоях питания.
*   **Минусы:** Нет.

## ADR-0012: Переход к OOP и разделению ответственности

### Контекст
Монолит 2700 строк с глобальным состоянием: трудночитаемость, риск race conditions, невозможность юнит-тестирования.

### Решение
Разбиение на классы: YadpylesosMain (оркестратор), DatabaseManager (DAL), DownloadEngine (скачивание/Circuit Breaker), ScannerAgent (скан/Mark-and-Sweep), TelegramService (уведомления). Позднее добавлены ScannerAgent-методы, SystemMonitor-логика, и экстракция провайдеров (ADR-0015).

### Последствия
*   **Плюсы:** CC всех функций ≤ 9; глобальное состояние устранено (кроме конфигурации); линтеры чистые.
*   **Минусы:** Тщательное тестирование после переноса бизнес-логики.

## ADR-0013: База телеметрии (агрегированный опыт)

### Контекст
Скрипт реагировал на баны и перегрев постфактум; не было «памяти» для анализа трендов. Реалтайм-запись метрик вызывала блокировки SQLite.

### Решение
Глобальная `telemetry.db`. Вместо реалтайма — агрегированные пики (температура, I/O, среднее время API) пишутся одной строкой в конце сессии. Позднее добавлена лента событий YouTube (`video_events`: 429, age-gate) — фундамент проактивного антибана.

### Последствия
*   **Плюсы:** Ноль блокировок во время скачивания; накопление опыта на конкретном железе; материал для пороговых политик антибана.
*   **Минусы:** Жёсткое падение (OOM-kill) теряет данные текущей сессии.

## ADR-0014: Гомеостаз 3.0 и Cynefin

### Контекст
Старый гомеостаз опирался только на Load Average — не отражал нагрузку RAID и троттлинг CPU.

### Решение
Класс мониторинга (интегрирован в оркестратор): 10 метрик каждые 60 сек — температура CPU, частота, Load, RAM, иноды, I/O-задержка. Принцип Cynefin: при недоступности сенсоров — плавная деградация (только Load и I/O).

### Последствия
*   **Плюсы:** Автоснижение потоков при захлёбывании диска (I/O > 2000 мс) или перегреве.
*   **Минусы:** Требует корректного проброса `/sys`-путей для конкретной модели NAS.

## ADR-0015: Экстракция модулей API и VPN

### Контекст
Для поддержки других облаков (Mail.ru) и чистоты ядра логика Яндекса и VPN должна быть изолирована.

### Решение
`YandexAPIService` вынесен в `apiyandex.py`, `VpnManager` — в `vpnmanager.py`. Круговые импорты решены паттерном ленивого импорта: модули подключаются внутри фабрики `__init__` оркестратора после загрузки конфигурации и логгера. Позже созданы `apivideo.py` (YouTube) и заглушка `apimail.py`.

### Последствия
*   **Плюсы:** Ядро похудело; провайдеры переиспользуемы; подготовка мультивендорности.
*   **Минусы:** Bash пробрасывает три Python-файла через `-v` (позднее — с учётом доп. модулей).

## ADR-0016: Архитектура логирования и удаление дубликатов

### Контекст
report/ засорялась дублями: Bash сохранял перехваченный вывод, Python писал свой детальный лог; имена путались.

### Решение
Полный отказ от сохранения логов в Bash-оркестраторе. Единственный источник — файл Python-движка (`ИМЯ_ДАТА.txt`). Логи сессий — `batch_ДАТА.txt`. Автоочистка старше 14 дней. Служебные команды не создают пустых логов.

### Последствия
*   **Плюсы:** report/ чистый; дублирование устранено; нагрузка на диск снижена.
*   **Минусы:** Жёсткое падение Python до инициализации логгера оставляет след только в консоли.

# Решения 2026 года (аудит F-01…F-127 и спринты 0–5, S7–S10)

## ADR-0017: Спринты 1–5 — SSOT портов, целостность данных, надёжность движка

### Контекст
Систематический аудит выявил четыре класса дефектов: мёртвые пути VPN (наследие mihomo→Xray: три живых пути на несуществующем порту 7890 при Xray на 10808/10809), риск тихой потери данных (перезапись source_links.txt при несовпадении заголовка; карантин БД, переносивший файл без -wal/-shm и рушивший при locked), маскировку ошибок (env-переменные читались без валидации, «занята» печаталась для любой ошибки SQLite, провал yt-dlp давал «успех» в TG), неработающие фичи (--vpn-test падал TypeError, --trace-mem требовал флаг -X, watchdog зависаний yt-dlp был мёртв).

### Решение
*   **SSOT портов:** Единый источник — `PROXY_PORT` из .env (SOCKS=PROXY_PORT, HTTP=PROXY_PORT+1), атрибут `http_proxy_url` провайдера. Все потребители (TelegramService, failover, deep-check, yt-dlp --proxy) читают его.
*   **Целостность данных:** source_links.txt перезаписывается только при физическом отсутствии файла; карантин БД — именованный каталог, полный перенос (db+wal+shm), locked/busy ≠ повреждение; resume-офсет с диска; DiskFull в MT-пути и safe_rename; endswith-маски очистки.
*   **Конфигурация:** Все env-переменные через валидирующие хелперы (_int_env/_float_env) на старте; мёртвые переменные удалены, живые оживлены (MAX_RETRIES, CHUNK_SIZE_MB, QUEUE_LIMIT); .env — честный SSOT.
*   **Надёжность движка:** Все ожидания через stop_event.wait (прерываемость по SIGTERM); DiskFull-путь в многопотоке; seen-флаг при upsert'ах; BrokenPipe → корректный exit 0; защита от вечного цикла в sanitize_filename.
*   **VPN-слой:** --vpn-test починен (генерация конфига по явному серверу); имя сервера больше не мутируется; ротация при бане поверх активного туннеля; автоочистка остановленных контейнеров по ancestor-фильтру.

### Последствия
*   **Плюсы:** Класс «тихая потеря данных» закрыт полностью; все объявления env-ручек соответствуют фактическому поведению; антибан-контур полностью прерываемый.
*   **Минусы:** Требуется дисциплина grep-контроля при каждом батче правок (выведено в правило процесса).

## ADR-0018: YouTube-подсистема и миграция VPN на Xray-core

### Контекст
YouTube-скачивание требовало: авторизации через куки (OAuth YouTube закрыт), решения JS-челленджей (n-challenge), устойчивости к ротации кук и bot-check, честной обработки провалов. Параллельно выявлено расщепление VPN-стека: код и .env исторически содержали пути mihomo (7890), образ собирал Xray — по факту работал только Xray.

### Решение
*   **Миграция VPN на Xray-core окончательно:** v26.7.28 (arm64), JSON-конфиг генерируется в коде (аналог PyYAML-решения ADR-0006), инбаунды SOCKS 10808 / HTTP 10809. Мёртвые mihomo-пути и переменные .env удалены.
*   **JS-челленджи:** Node.js 24 (NodeSource; Node 20 — вне гейта EJS yt-dlp) + скрипт-решатель из официальной дистрибуции EJS, живущий в persistent-кэше на хосте (`cache/yt-dlp/`, монтирование /cache-yt): сеть в сессии для решателя не участвует. Кэш прогревается одним успешным прогоном и живёт до несовместимости версий.
*   **Куки-модель:** экспорт из инкогнито-вкладки с немедленным закрытием; yt-dlp самообслуживает файл; признаки ротации парсятся и доставляются в Telegram («Куки ротированы», «Контент 18+», «OAuth закрыт»).
*   **PO-токен (bgutil):** сервер 1.3.2 в образе (/opt/bgutil, собранные исходники из build_assets), pip-плагин того же пина; провайдер поднимается на время сессии (:4416) и прогревается до старта yt-dlp; лог — report/bgutil_provider.log.
*   **Честные коды возврата:** провал сессии (rc≠0 или 0 скачанных) → exit 1 + Telegram с человеческой причиной; имперсонация (curl_cffi) для снижения бот-детекта.

### Последствия
*   **Плюсы:** Качество 18+ ограничено только SABR-политикой YouTube (внешний фактор); bot-check защищён; инфраструктура готова к изменениям YouTube; VPN-стек един и верифицирован (--vpn-test).
*   **Минусы:** SABR-потолок 360p для age-gated — внешнее ограничение, не устраняемое на нашей стороне; bgutil-сервер добавляет ~100-150 МБ RAM на сессию (принято, D-051).

## ADR-0019: Проактивный антибан (ступень А) и телеметрия видео

### Контекст
Антибан был реактивным на уровне отдельных запросов; лента событий YouTube не собиралась; телеметрия видео-провайдера писала нули (путь не кормил БД). Долгосрочная цель — проактивные политики на накопленном опыте.

### Решение
*   **Телеметрия видео:** api_sessions дополнились честными числами видео-сессий (попытки, 429, средняя стоимость элемента); новая таблица video_events (timestamp, event: extract/429/antiban_abort) — материал для пороговых политик.
*   **Ступень А (сессионный кумулятив):** серия ANTIBAN_429_SERIES (по умолчанию 5) событий 429 без успешных извлечений между → прерываемая пауза ANTIBAN_PAUSE_SEC (60с, через stop_event); три паузы подряд без успеха → «достойный отступ»: чистая остановка сессии, TG с инструкцией. Давление сбрасывается успешными извлечениями.
*   **Ступень Б (прогностический профиль):** при старте сессии — SQL-анализ частоты 429 за окно (7 дней) → профиль обычный/осторожный/минимальный → CLI-переопределения sleep-аргументов yt-dlp (конфиг не редактируется). Внедряется после накопления 5–7 дней боевой телеметрии.

### Последствия
*   **Плюсы:** Штормовые ситуации (рейт-лимит) гасятся автоматически без участия пользователя; Telegram информирует один раз, а не спамит; данные для будущих политик копятся пассивно.
*   **Минусы:** Серия 429 субтитров и серии основного потока неразличимы в ступени А (консервативно — пауза чуть раньше необходимого); разделение типов — кандидат при накоплении данных.
