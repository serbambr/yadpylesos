# База инструментов и принципов инженерии (60 шт.)

Универсальная база междисциплинарных методологий, паттернов и принципов для разработки надежных систем.

## 1. Управление проектами и процессами

1. **FMEA (Анализ видов и последствий отказов):** Предотвращение ошибок до их возникновения путем оценки тяжести, вероятности и обнаруживаемости.
2. **MoSCoW:** Приоритизация задач (Must have, Should have, Could have, Won't have).
3. **PDCA (Цикл Деминга):** Непрерывное улучшение (Plan-Do-Check-Act).
4. **5S:** Организация рабочего пространства и кода (Сортировка, Соблюдение порядка, Содержание в чистоте, Стандартизация, Совершенствование).
5. **Just-in-Time:** Разработка ровно того, что нужно сейчас, без "про запас".
6. **VSM (Картирование потока создания ценности):** Выявление узких мест и задержек в процессе поставки ПО.
7. **Эвристическая оценка (UX):** Оценка удобства использования системы на основе эмпирических правил.
8. **TRL (Уровни готовности технологий):** Оценка зрелости функции (от прототипа до продакшена).
9. **Шесть шляп:** Метод параллельного мышления для всестороннего анализа решений (Белая-факты, Черная-риски, Желтая-плюсы, Зеленая-идеи, Красная-эмоции, Синяя-процесс).
10. **Парето (80/20):** Фокус на 20% усилий, которые дают 80% результата.

## 2. Архитектура и проектирование

11. **Бритва Оккама:** Не плодить сущности без необходимости. Выбирать самое простое решение.
12. **SSOT (Единый источник истины):** Данные не должны дублироваться; должна быть одна эталонная система хранения.
13. **Идемпотентность:** Свойство операции, при котором многократное ее выполнение дает тот же результат, что и однократное.
14. **Разделение ответственности (Separation of Concerns / ДНК/РНК):** Разбиение системы на модули с четко определенными границами.
15. **Auftragstaktik (Миссионерское командование):** Договариваемся о контракте (вход/выход), внутреннюю реализацию исполнитель выбирает сам.
16. **Многоуровневая архитектура:** Разделение системы на слои (например: Представление, Бизнес-логика, Доступ к данным).
17. **Антикоррупционный слой (ACL):** Изоляция ядра системы от внешних "грязных" форматов данных через адаптеры.
18. **CQRS (Разделение команд и запросов):** Разделение операций изменения состояния и чтения данных.
19. **Сага (Компенсирующие транзакции):** Управление распределенными транзакциями через последовательность локальных операций с возможностью отката.
20. **Предохранитель (Circuit Breaker):** Временная блокировка вызовов к сервису при превышении лимита ошибок для предотвращения каскадных сбоев.
21. **Переборка (Bulkhead):** Изоляция ресурсов (пулов потоков, соединений), чтобы отказ в одной части не "потопил" всю систему.
22. **CAP Теорема:** Осознанный выбор между Консистентностью, Доступностью и Устойчивостью к разделению в распределенных системах.
23. **Закон Деметры:** Модуль не должен знать внутреннее устройство объектов, с которыми работает.
24. **Теория игр:** Моделирование взаимодействия сторон (например, бота и антибот-системы) для выбора оптимальной стратегии (Равновесие Нэша).
25. **Инверсия управления (IoC):** Делегирование управления зависимостями внешнему контейнеру или фреймворку.
26. **Микро-патчи (Атомарность):** Разбиение сложных фич на минимальные, тестируемые изменения.
27. **State-Transition (Переходы состояний):** Жесткий контроль жизненного цикла объектов (Создан -> Запущен -> Остановлен).
28. **Mark and Sweep:** Алгоритм инкрементального обновления кэша (пометка -> обновление -> сборка мусора).
29. **Согласованность в конечном счете (Eventual Consistency):** Допущение временного рассинхрона данных с их последующей гарантированной синхронизацией.
30. **Гравитационные системы:** Автоматическая очистка ресурсов (уборка мусора) при завершении работы.

## 3. Анализ, качество и тестирование

31. **Root Cause Analysis (5 Почему):** Поиск корневой причины бага, а не лечение симптомов.
32. **Бремя доказывания (Burden of Proof):** Любое утверждение об оптимизации должно подтверждаться бенчмарками или логикой.
33. **Двойное слепое тестирование:** Проверка скрытыми данными, чтобы исключить эффект "работает у разработчика".
34. **Мутационное тестирование:** Проверка качества тестов путем искусственного внесения ошибок в код.
35. **Эффект Хоторна:** Изменение поведения системы/пользователя при осознании факта наблюдения.
36. **Цикломатическая сложность (McCabe):** Метрика сложности кода; ограничение количества ветвлений в функциях (CC < 10).
37. **Фаззинг (Red Teaming):** Тестирование системы на устойчивость к "мусорным" или злоумышленным входным данным.
38. **DOE (Планирование экспериментов):** Систематический подход к подбору параметров для бенчмарков.
39. **Двойное слепое тестирование:** Проверка скрытыми данными, чтобы исключить эффект "работает у разработчика".
40. **BDD (Behavior-Driven Development):** Разработка через поведение. Фиксация сценариев (Дано-Когда-Тогда) перед написанием кода.
41. **Unit Testing:** Автоматизированное тестирование изолированных "чистых" функций.
42. **Хаос-инжиниринг (Chaos Engineering):** Намеренное внесение сбоев в продакшен для проверки устойчивости системы.
43. **Стресс-тестирование:** Проверка поведения системы при запредельных нагрузках.
44. **Прослеживаемость (Traceability):** Связь каждой строчки кода с бизнес-требованием.
45. **Альтернативные издержки:** Оценка стоимости времени разработки одной фичи в ущерб другой.

## 4. Безопасность и надежность

46. **Zero Trust (Нулевое доверие):** Проверка всех входных данных, отказ от доверия внутренней сети.
47. **Принцип Керкгоффса:** Безопасность системы не должна зависеть от скрытности алгоритма, только от ключа.
48. **Default to Safe (Принцип дефолтного выбора):** При нештатных ситуациях система выбирает самый безопасный режим.
49. **Defense in Depth (Эшелонированная оборона):** Многоуровневая защита (сеть -> ОС -> приложение -> БД).
50. **Jidoka (Автономизация):** Остановка конвейера при обнаружении дефекта.
51. **Poka-Yoke (Защита от дурака):** Проектирование системы так, чтобы совершить ошибку было невозможно.
52. **Fail-Fast:** Быстрое падение системы при невалидных данных для предотвращения потери ресурсов.
53. **Апоптоз (Программируемая гибель):** Мгновенное завершение работы при критических ошибках ОС для защиты данных.
54. **Graceful Degradation (Плавная деградация):** Сохранение частичной работоспособности при сбое внешних компонентов.
55. **Антихрупкость:** Способность системы становиться сильнее после стресса.
56. **Гомеостаз:** Автоматическая адаптация к нагрузке (снижение потоков при перегреве).
57. **Аудит-трейл (Черный ящик):** Полное логирование действий для восстановления цепочки событий.
58. **STRIDE (Модель угроз):** Спуфинг, Подмена данных, Отказ в обслуживании, Раскрытие информации, Повышение привилегий.
59. **Cynefin:** Фреймворк для принятия решений в различных средах (Простые, Осложненные, Комплексные, Хаотичные).
60. **Цикл OODA:** Быстрый цикл наблюдения, ориентации, решения и действия для адаптации к меняющейся среде.
