# Архитектурный манифест: Я.Д-Пылесос (YA.D-Pylesos)

Документ описывает инженерный подход, применённый при разработке утилиты для скачивания данных с Яндекс.Диска и YouTube на NAS-серверы Linux arm64 / x86-64.

Разработка ведётся с применением AI-Assisted Development (LLM). Автор выступает в роли Product Owner / Project Manager / System Architect / QA Engineer, формулируя архитектурные принципы и ограничения, применяя междисциплинарные методологии аудита и проводя краш-тесты. ИИ используется в роли разработчика для генерации boilerplate-кода и реализации бизнес-логики под контролем автора.

### 1. Фундаментальные принципы (Ограничения среды)

Проект изначально проектировался как инфраструктурный компонент, работающий 24/7 на слабом железе с механическими дисками. Заложены принципы:

*   **Анти-бан API (Мимикрия):** Абсолютный приоритет минимизации вероятности блокировки IP-адреса над скоростью. Алгоритм ведёт себя как человек: гауссовы паузы, рандомизация, реакции на давление.
*   **Бережливость HDD (RAID-friendly):** Абсолютный приоритет корректной физической записи над скоростью. Многопоточная запись не фрагментирует ФС и не убивает IOPS.
*   **Безопасность данных (ACID & Zero Trust):** Ни один битый файл не заменяет оригинал. Операции с диском и БД атомарны. Входные данные строго валидируются (аргументы, кэш, env-переменные).
*   **Самоисцеление и Graceful Degradation:** При обрыве связи, сбое питания или падении контейнера работа продолжается с точки остановки. При критических сбоях — плавная деградация или Fail-Fast.

### 2. Аудит надежности (FMEA и кросс-дисциплинарные методы)

Для поиска скрытых уязвимостей применялись FMEA и инструменты из смежных дисциплин (проектный менеджмент, авиация, медицина, юриспруденция, биология).

**Выявленные и устранённые угрозы (исторические):**

*   **Атомарность склейки (RPN 270):** Моргание света при склейке `.part.N` оставляло недоклеенный файл. *Решение:* маркер `.gluing` — при рестарте все куски удаляются и файл качается заново; финальное переименование — `os.replace`.
*   **Хаотичные сбои (Cynefin):** При критических ошибках ФС (Read-Only, ENOSPC, иноды) скрипт не «выживает», забивая логи. *Решение:* Апоптоз — мгновенное завершение (Fail-Fast) + предстартовая проверка места/инодов.
*   **Блокировка БД:** Параллельные контейнеры блокировали единую SQLite. *Решение:* BL-DB-Split — по файлу БД на ссылку; глобальные `.lock` удалены как атавизм. Транзиентные блокировки (locked/busy) отличимы от повреждения и не приводят к карантину.
*   **Обнуление БД на лету:** Повреждённая БД переносится в карантин **целиком** (включая `-wal`/`-shm`, в именованный каталог), создаётся пустая, работа завершается для перестроения кэша.

**Дополнено аудитами спринтов 2026 года (F-01…F-127):** защита `source_links.txt` от перезаписи при несовпадении заголовка; точные суффиксы при очистке (`.part`-маска); resume-офсет с диска вместо БД; DiskFull в многопоточном пути; квоты (EDQUOT) → Апоптоз; env-валидация на старте; честные коды возврата yt-dlp → Telegram.

### 3. Архитектура данных и памяти (SSOT, DAL, Mark-and-Sweep)

Изначально карта диска и дерева Яндекса жила в оперативной памяти: 40 000+ файлов давали 800 МБ RAM с риском OOM-kill.

*   **SSOT:** Словари RAM удалены; единственный источник истины — SQLite (WAL). Кэш дерева, очередь, MD5 — в БД.
*   **Mark and Sweep:** Повторный запуск не сканирует диск заново: сверка `mtime`+размер, флаг `scanned`. Износ RAID минимизирован.
*   **Streaming Queue:** Очередь берётся из БД по одному (`LIMIT 1`).
*   **Телеметрия:** `db/telemetry.db` — глобальная БД опыта: итоги сессий по провайдерам (запросы/баны/пиковые метрики) и лента событий YouTube (`video_events`: 429, age-gate) — фундамент проактивного антибана. Запись — одна строка в конце сессии (ноль блокировок в процессе).
*   **Профилирование:** `--trace-mem` (tracemalloc), тесты на 65 000 файлов — < 100 КБ RAM на состояние.

### 4. Физика дисков и оптимизация IOPS

*   **Bulkhead:** Многопоточность — не `seek` в один файл, а изолированные `.part.0/.part.1`: Random Write превращён в Sequential.
*   **Гомеостаз:** Мониторинг Load Average, температуры CPU (проброс сенсора через volume), частоты, I/O-задержки записи. Перегрузка → снижение потоков; восстановление → возврат к исходным.
*   **I/O-наблюдаемость:** Замер задержки каждой записи; пиковые значения уходят в телеметрию.
*   **Автоочистка артефактов:** Обрывки сессий (`.part`, `.fNNN.*`, `.temp.*`) старше часа удаляются при старте новой — без риска для параллельных загрузок.

### 5. Сетевая устойчивость, анти-бан и VPN

**Яндекс (API + CDN):** взаимодействие спроектировано на основе теории игр (AIMD):

*   **Адаптивные паузы:** 200 OK — пауза сокращается; 429 — резко растёт. `Retry-After` уважается с надбавкой.
*   **Детекция тихого бана:** HTML вместо JSON — блокировка; смена User-Agent, бэкофф.
*   **Адаптивный CDN:** Обрывы связи наращивают паузы между чанками.
*   **VPN (Xray-core, SSOT портов):** При банах/блокировках — туннель из пула `vpn/link*.txt` (VLESS/Trojan/Hysteria; Reality). Единый источник порта — `PROXY_PORT` из `.env` (SOCKS 10808 / HTTP 10809). Failover переключает обе сессии (API+CDN); при активном VPN и повторных банах — ротация на следующий сервер; исчерпание — Апоптоз. Аудит смен IP — `vpn_audit.log`.
*   **Watchdog:** Фоновый мониторинг процесса Xray (poll) и туннеля (тестовый запрос): падение — ротация; зависание (5 промахов) — принудительный kill и ротация.

**YouTube (yt-dlp-подсистема):**

*   **Двухуровневый анти-бан:** Ядро AIMD (см. выше) + ступень «А»: серия 429 → прерываемая пауза; паузы не помогают → «достойный отступ» — чистая остановка сессии с уведомлением. Ступень «Б» (прогностический профиль по телеметрии) — в разработке.
*   **JS-челленджи:** Решаются Node.js runtime через EJS-механизм yt-dlp; скрипт-решатель живёт в persistent-кэше на хосте (сеть в сессии не участвует).
*   **PO-токен (bgutil):** Локальный провайдер Proof-of-Origin (Node, :4416) поднимается на время сессии и прогревается до старта yt-dlp. Защита от bot-check; для age-gated контента форматы ограничены SABR-политикой YouTube (потолок 360p) — не дефект реализации.
*   **Impersonation:** curl_cffi — TLS-отпечаток браузера для снижения бот-детекта.

**Boosty (через yt-dlp):**

*   Посты авторов (`boosty.to/<автор>/posts/<id>`) по подписке — куки сессии в `auth/boosty.to.txt` (маркер залогиненности — кука `auth`).
*   Медиа-галереи постов (включая full_hd) качаются универсальной yt-dlp-обёрткой; антиколлизия имён — `[id]` в имени файла.
*   Особенности платформы: контент на уровнях подписки (видимость = права аккаунта), HLS/DASH-манифесты, короткоживущие подписанные URL.

### 6. Экстракция модулей и круговые импорты

*   **Модули:** `apicloudyandex.py` (Яндекс-API), `apivideo.py` (YouTube и другие yt-dlp-платформы: Boosty и семейство подписочных), `vpnmanager.py` (Xray), `apicloudmail.py` (заглушка Mail.ru). Ядро — `yadpylesos.py` (оркестратор, DAL, движок, телеметрия). Диспетчеризация провайдеров — по домену ссылки; домены без спец-логики идут через универсальную yt-dlp-обёртку.
*   **Паттерн ленивого импорта:** Модули провайдеров импортируются внутри `__init__`-фабрики ядра после загрузки конфигурации и логгера — круговые импорты разорваны, модули переиспользуемы.
*   **Контракт провайдера:** ядро вызывает единый интерфейс (`fetch_*`, `map_*`, `process_*`), реализация — за провайдером.

### 7. Качество кода и наблюдаемость

*   **Design by Contract:** Контракты размеров/инвариантов; нарушение — ValueError, битые данные невозможны.
*   **Конвейер качества:** `./check.sh` — py_compile + ruff (правила E/F/W + C901, порог сложности 9) + radon (независимая верификация CC) + vulture (мёртвый код, whitelist по контрактам) + shellcheck. Все проверки зелёные — конвейер гейтит изменения.
*   **Env-гигиена:** Все переменные окружения читаются через валидирующие хелперы на старте; мусор в `.env` даёт человекочитаемый SystemExit.
*   **Честные коды возврата:** Провал сессии (в т.ч. YouTube) — exit 1 + Telegram с переведённой причиной; пустые/маскирующие ошибки устранены.
*   **Оркестрация (SSOT):** Управление ссылками — Python CLI (readline, csv); Bash — тонкий клиент Docker. `source_links.txt` монтируется rw поверх read-only каталога конфигурации.
*   **Bus Factor:** Логи самообъясняющиеся (эмодзи, цветовые уровни); детальный лог сессии в `report/` — источник истины (консоль docker logs может склеивать строки).

### Тестирование

NAS QNAP D4 arm64 (HDD WD UltraStar RAID1) и Fedora 44 WS SSD. Объёмы: ссылки до 3.5 ТБ и 65 000 файлов. Режимы: анонимный, OAuth 2.0, cookies (Яндекс), cookies YouTube (включая age-gated 18+), cookies Boosty (закрытые посты подписки). Приёмочные сценарии по спринтам: VPN-ротация, честные коды возврата, env-валидация, целостность БД, кэш решателя, PO-токен.

### Технологический стек

*   **Ядро:** Python 3.12 (Threading, SQLite3/WAL, requests, PyYAML, curl_cffi).
*   **YouTube-движок:** yt-dlp (runtime-обновление с VPN-фолбэком), Node.js 24 (EJS-челленджи), bgutil-ytdlp-pot-provider 1.3.2 (PO-токен).
*   **VPN-движок:** Xray-core v26.7.28 (arm64, бинарник в `build_assets/`).
*   **Инфраструктура:** Docker (python:3.12-slim, зеркало Debian, NodeSource).
*   **Оркестрация:** Bash (GNU Coreutils; QTS bash, BusyBox — вспомогательный).
*   **Аудит:** FMEA, TRIZ, Cynefin, Ruff, Radon, Vulture, ShellCheck.

### Перспектива (Долгосрочное развитие)

*   **Ступень «Б» антибана:** Прогностический профиль сессии по телеметрии (частоты 429 → адаптивные sleep-профили).
*   **Proactive health:** Детект «среда сломана» по однородным ошибкам (досрочная честная остановка).
*   **Windows-порт:** Перенос оркестратора Bash → Python (psutil).
*   **Cron-ночные смешанные выгрузки:** Яндекс + YouTube по расписанию.
*   **18+ выше 360p:** Пересмотр при изменении SABR-политики YouTube / поддержке новых клиентов провайдером.
